Replacing a university computer lab with 24 new Macs

Marymount University has computer labs where students and staff can walk in and use a computer. One of those labs was still running old iMacs. As an intern in the university's IT department, I co-led a small team of interns that swapped the whole lab over to 24 new Macs, from setting them up to making sure the IT office could manage them remotely. About four interns contributed over six weeks, and another intern and I did most of the work.

The situation

Replacing a lab is more than plugging in new computers. Each Mac needs the right software, a standard name so IT can track it, and security settings so it can't be tampered with. The old iMacs also had to be wiped before they left, so no student or staff data went with them.

The result

The lab is now running on new hardware, and the IT office can update and troubleshoot every machine from their desks instead of walking over to the lab.

What I did, step by step

  1. 1

    Set up

    Updated each new Mac, installed the software that had been requested for the lab, and wrote down the setup so it could be repeated.

  2. 2

    Track

    Named each Mac using the university's naming standard and recorded its serial number and network (MAC) address in IT's inventory database.

  3. 3

    Retire the old ones

    Removed the old iMacs and securely wiped their drives so no data left the building with them.

  4. 4

    Install

    Set the new Macs and their keyboards, mice and other equipment up in the lab, and locked them down physically.

  5. 5

    Make it manageable

    Fixed Screen Sharing (the tool IT uses to see and control a Mac remotely), which had broken after a change in Microsoft Intune, the system that manages university devices. Then recorded each Mac's network address so IT could reach it.

Fixing a classroom projector problem with a script

Classrooms at the university have a Windows computer hooked up to both a monitor and a projector. The projector is supposed to mirror the monitor, so the class sees exactly what the instructor sees. On Windows this is called "Duplicate" mode, the option you get by pressing Win + P. In several classrooms that setting kept failing, so I wrote a small program that sets it automatically.

The problem

On several classroom computers, Duplicate mode kept failing at login, which led to repeated complaints about the projector. Fixing it by hand in each room didn't stick, because the problem came back.

What I did

I wrote a Python script that asks Windows directly for Duplicate mode, the same thing Win + P does. Projectors can take a few seconds to wake up after login, so it retries up to five times and writes each attempt to a log file IT can check later. I packaged it as a regular Windows program (.exe) and used Task Scheduler, a built-in Windows tool that runs programs automatically, to run it every time someone logs in.

The result

The classroom computers now set the projector to mirror the screen on their own at every login, fixing a recurring problem across multiple classrooms.

The core of the script

This function makes the one Windows call that switches the display. The rest of the script handles retries, error messages and logging.

def set_duplicate_mode() -> int:
    """Ask Windows to apply the clone/duplicate topology."""
    user32 = ctypes.WinDLL("user32", use_last_error=True)
    set_display_config = user32.SetDisplayConfig
    set_display_config.argtypes = [
        ctypes.c_uint32, ctypes.c_void_p, ctypes.c_uint32,
        ctypes.c_void_p, ctypes.c_uint32,
    ]
    set_display_config.restype = ctypes.c_long

    # Win32 equivalent of DisplaySwitch.exe /clone
    flags = SDC_APPLY | SDC_TOPOLOGY_CLONE
    return int(set_display_config(0, None, 0, None, flags))

Building, checking and tearing down a cloud server automatically

Companies increasingly rent servers from cloud providers like Amazon Web Services (AWS) instead of buying their own. Setting those servers up by hand is slow and easy to get wrong, so IT teams write code that does it for them, and use a "pipeline" that runs that code step by step. For a class project, I built a pipeline that creates a web server on AWS, sets it up, checks that it meets the rules, and deletes it when it's no longer needed.

The goal

Go from nothing to a running, configured web server on AWS without clicking through any settings by hand, so the whole setup can be rebuilt exactly the same way any time.

What I used

Terraform creates cloud resources from a written description. Ansible logs into a server and sets it up from a list of instructions. InSpec automatically checks that the setup follows the rules. GitLab CI runs all of them in order.

Why it matters

This approach, known as "infrastructure as code," is how many IT teams manage servers today: every change is written down, repeatable and can be reviewed before it happens.

How the pipeline runs

  1. 1

    Validate

    Checks the infrastructure code for mistakes.

  2. 2

    Plan

    Shows exactly what will be created before anything changes.

  3. 3

    Build

    After a person approves, Terraform creates the server, its two disks and its firewall rules on AWS.

  4. 4

    Configure

    Ansible installs and starts the Apache web server and publishes a web page.

  5. 5

    Check

    InSpec confirms the server exists, is running, uses the approved Linux image and is tagged correctly.

  6. 6

    Tear down

    After approval, Terraform deletes everything so nothing keeps running and costing money.

Security was part of the design: the server only accepts remote logins from the pipeline itself, not the whole internet, and no passwords or keys are stored in the code.
